# 交易链路设计原则与模式

基于《企业应用架构模式》及交易系统实践，将设计原则与模式映射到交易链路（下单、履约、逆向退款等）的设计与评审场景。

---

## 设计原则

### 单一职责原则（SRP）

- **要点**：一个类/模块只有一个变化原因；交易场景下优先按**业务活动**划分入口与流程。
- **落地**：
  - 履约、逆向退款等不同业务活动使用**独立服务入口**和 BPM，便于限流、错误定义、回归测试独立发展、影响面可控。
  - 避免“一个通用服务 + 内部大量路由”的臃肿入口；通用能力用切面等解决。
  - 再往下（流程、节点、能力、扩展）是否共用的判断依据：**能力差异度、场景复杂度、开发与维护成本**；不同系统风格可不同：
    - **履约**：多按能力维度沉淀，同一能力内兼容多场景（如打款扩展点同时服务确认收货、退并打、定金罚没等）。
    - **逆向退款**：扩展尽量按业务活动独立（如买家申请退款、卖家同意、买家退货等各自扩展点），减少漏改但需注意独立过多时的场景遗漏。
- **评审**：入口是否按业务活动隔离？下层复用是否与“单一变化原因”匹配？

### 开闭原则（OCP）

- **要点**：对扩展开放，对修改封闭；核心逻辑稳定、扩展逻辑可插拔。
- **落地**：
  - **业务与平台隔离**：核心流程与节点由平台控制、尽量通用少改；扩展（TMF/星环、域扩展、产品包/APP 包）由业务理解与调整。
  - **域内扩展**：如支付可走直连支付宝或经支付系统接微信等，通过扩展机制接入，不修改核心流程。
  - **业务包内**：多行业/多场景可再次用策略、责任链等做路由与扩展。
- **边界注意**：
  - 业务身份是技术隔离手段，冲突前置到解析；实际圈品等可能跨“业务”，产品包可叠加业务但需防“漏叠”。
  - 业务与平台的边界可随权责变化（如域扩展中的特殊业务能力、fork 独立演进、商业能力归属），遵循**权责一体**。
- **评审**：核心是否少动？扩展点是否清晰、可插拔？

### 里氏替换原则（LSP）

- **要点**：子类/实现可替换基类/抽象而不影响行为；面向抽象编程，替换顺畅度取决于抽象是否合理。
- **落地示例**：
  - 扩展点定制：不关心是业务包还是场景产品包，只关心定制结果。
  - 数据源：不关心订单库/历史库/外部服务（如评价），只关心查询结果。
  - 支付：不关心支付宝/微信等具体渠道，只关心支付/退款结果。
- **注意**：替换往往难以完全无感——服务保障（SLA）、实现能力（如历史库能力降级）、协议（错误码、退款时效等）可能不一致，需额外稳定性与兼容设计。
- **评审**：抽象是否稳定？替换实现时是否有隐藏的保障/协议差异需要显式处理？

### 迪米特法则（LoD）

- **要点**：只与直接朋友交互；减少实体间耦合与“知识”。
- **落地**：
  - **协调层**：用一套基础流程 + 节点 + **上下文**（Request/Result/Context）协调各域；数据从上下文取、回写上下文（回收），避免域间直接传递。
  - **入口系统**：下单等入口作为协调者，调用商品、库存、营销、资金、履约等，系统间少直接互调。
  - 协调者做调用与 convert，从而可：精简模型、控制只读、懒加载等。
- **权衡**：协调者会随参与者增多变重；共享模型/“各参与者一块固定区域”可减 convert，但若有隐晦过程逻辑或聚合根，分散数据中心难以保证一致性；开发时“知名”的上下文通常比分散中心更易定位。
- **评审**：是否有清晰的协调者与上下文？数据传递是否收敛、可管控？

### 接口隔离原则（ISP）

- **要点**：客户端不依赖不需要的接口；依赖建立在最小接口上。
- **落地**：
  - 按**读写**隔离：读一套、写一套。
  - 按**角色**隔离：买家/卖家/小二等各一套。
  - 按**端/协议**隔离：PC/H5/客户端，或奥创/Astore/DTO 等各一套。
  - 好处：客户端依赖更小；服务端可独立演进，复用部分放 share/common。
- **例外**：当接口数量大、且需复用客户端通路时，可保留**入口层**通用接口（如 doOp + 操作 code），内部仍按 code 严格正交路由到不同策略。
- **评审**：接口是否按使用方与协议做了最小化拆分？是否存在“大而全”的接口可拆？

### 依赖倒置原则（DIP）

- **要点**：依赖抽象接口而非具体实现；降低客户与实现的耦合。
- **落地**：
  - 底层稳定、无多实现时：可直接依赖具体（如订单域内把查询当 Repo 直接调用）。
  - 外部/不可控服务：加**网关/抽象层**，依赖接口不依赖实现（如下单、履约中的 gateway）。
  - 抽象层理想上独立 jar/库；若放在 A 或 B 子模块，需单独打包，略繁琐。
- **交易场景难点**：复杂领域对象 + 多 convert + 与 DB 模型映射，易导致“数据从哪带出”难以追踪；有时**紧耦合 + 可追踪**比过度抽象更可维护。
- **评审**：外部/多变依赖是否通过抽象隔离？抽象层是否带来可接受的复杂度？

## 设计模式在交易链路的映射

| 模式 | 在交易中的典型用法 |
|------|-------------------|
| **模板（Template）** | 流程骨架 + 可扩展节点；平台编排 + 业务扩展点，形成平台与业务融合。 |
| **责任链（Chain of Responsibility）** | 商业能力/域扩展执行时遍历插件，按回收规则熔断；如 TMF 执行引擎遍历产品包/APP 包，首个返回 true（如“跳过通知支付”）即停止。 |
| **策略（Strategy）** | 多种算法可切换；如逆向退款的多出账策略（担保交易、保证金、微信、退卡/退资产等），扩展点定制，可单策略或多策略执行。 |
| **观察者（Observer）** | 系统间通过消息注册/回调；如 0s 退监听退款创建消息触发同意，异步解耦 + 利用重投提高成功率。 |
| **状态（State）** | 工作流定义状态与每状态可执行操作；如担保交易：创建外部支付交易→付款回调→创建物流单→发货→确认收货，每节点限定可做操作（如未付款不可打款/退款）。 |
| **中介者（Mediator）** | 大上下文协调各域数据；各编排节点写上下文，最终由更新节点统一落库，避免节点间直接耦合。 |
| **组合（Composite）** | 递归描述层次结构；如下单拆单，订单不断分组、递归细化。 |
| **单件（Singleton）** | 外部调用资源库（如订单、评价、图标、超时等 Repo）以单例获取，便于工具类静态调用。 |
| **解释器（Interpreter）** | 动态脚本/规则配置（如牛顿）；通过解释表达式减少部署成本。 |
| **代理（Proxy）** | 对上下文做只读包装，进入执行节点时转为只读接口代理，防止域内篡改。 |

## 使用本 Skill 时的建议

1. **设计/评审交易流程时**：先看入口与流程是否满足 SRP、协调层是否满足迪米特与中介者；再看扩展点是否满足开闭、里氏替换与策略/责任链。
2. **设计/评审接口与依赖时**：检查接口隔离与依赖倒置是否合理，是否在“可维护性”与“可追踪性”之间取得平衡。
3. **引用原则与模式时**：优先用“原则 + 交易案例”说明设计意图，用“模式 + 在交易中的用法”说明结构选择，避免空谈概念。
